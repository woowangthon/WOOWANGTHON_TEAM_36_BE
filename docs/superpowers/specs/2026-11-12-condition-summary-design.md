# 조건 요약 설계 (추출 프롬프트 v10)

- 작성일: 2026-11-12
- 상태: 사용자 검토 대기
- 브랜치: `feat/T43-condition-summary` (`feat/T41-display-name` b491dc8에서 분기, T41 머지 뒤 `main`으로 rebase)
- 카드: T43(backend), T44(frontend)

## 1. 목적

배포된 상세 화면에서 조건 설명이 읽기 어렵다는 문제가 4가지 나왔습니다.

| # | 문제 | 원인 |
| --- | --- | --- |
| 1 | "「충북대학교 등록금재원 장학금 관리지침」을 따름" 같은 안내 문장이 조건처럼 보임 | v8 프롬프트가 이 문장을 `basic_conditions`에 넣게 하고, 화면은 이 목록을 "지원 전 확인"으로 보여 줍니다(골든셋 v8 결과 sw_dept_1154016에서 확인) |
| 2 | 설명이 길고 어색함. 예: "먼저, 지방 국립대학교[참고1]에 진학하는 학생은 … 등록금을 전액 지원받을 수 있습니다" | 세 목록과 `evidence` 모두 원문을 그대로 넣고, 화면도 원문을 그대로 보여 줍니다. 이 예시 문장은 v8부터 `notes` 예시로 프롬프트에 있으나, 배포 데이터는 v8 배포(2026-11-12 18:35) 전에 추출된 뒤 재추출하지 않은 것으로 보입니다 |
| 3 | 부정문이라 충족/불충족으로 답하기 어려움. 예: "휴학예정 학생 제외" | 직접 답하는 조건이 원문 그대로 질문이 됩니다. 제목은 프론트 단어 규칙(`conditionLabel.ts`)이 붙이는데 대부분 "기타 조건"입니다 |
| 4 | ✓/✗와 직접 답하는 조건 모두 설명이 장황함 | 2와 같음 |

조건마다 **짧은 요약 한 줄**을 보여 주고, 원문은 근거로만 남기는 것이 목표입니다. 판정 규칙(5.3)은 바꾸지 않습니다.

## 2. 결정 사항

| 항목 | 결정 |
| --- | --- |
| 요약을 만드는 곳 | 목록 문장(`extra_conditions`·`basic_conditions`)은 **추출 때 Gemini**가, ✓/✗ 조건은 **코드**가 추출된 값으로 만듭니다. 사용자 조회 때 LLM을 부르지 않습니다 |
| 요약 범위 | `extra_conditions`와 `basic_conditions`만 요약합니다. `notes`는 조건이 아닌 안내이므로 원문 그대로 둡니다 |
| 화면 답 문구 | 바꾸지 않습니다. 상세는 "충족 / 불충족 / 모름", 빠른 확인 카드는 "이 조건에 맞나요?" + "맞아요 / 안 맞아요 / 모르겠어요"입니다(FE #54). 요약을 긍정형으로 써서 "맞아요 = 충족"이 되게 합니다 |
| 조건이 아닌 출처 문장 | 세부 자격이 **같은 공지에 적힌** 규정의 출처 문장과 소제목은 어느 목록에도 넣지 않습니다. 세부 자격이 입력에 없는 외부 기준 참조는 지금처럼 `extra_conditions`입니다 |
| 요약 극성 검증 | eval 결과 파일에 `원문 → 요약` 목록을 따로 출력하고, v10을 머지하기 전에 사람이 한 번 확인합니다. 자동 채점은 하지 않습니다 |
| 원문 표시 | 직접 답하는 조건은 요약 아래 원문을 2줄까지 보여 줍니다(요약이 틀렸을 때 대조용). ✓/✗ 조건과 "지원 전 확인"은 원문을 "근거 보기"로 접습니다 |
| API 호환 | 웹 API는 필드 추가만 합니다(4.2). backend와 frontend 배포 순서가 자유롭습니다 |
| 기존 데이터 | 마이그레이션 없이 읽힙니다(4.1). v10 배포 뒤 모집 중·상시 공지를 관리자 재추출합니다 |
| 관리자 화면의 `model_version` 표시 | 이번 범위가 아닙니다(계획서에 없음). 재추출 완료는 DB 쿼리로 확인합니다 |

## 3. 요약 문장 규칙

### 3.1 목록 문장 요약 (Gemini, `summary`)

- 25자 안쪽의 **명사형 자격 문구**입니다. "~인 학생", "~함", "~없음"으로 끝냅니다. "이 조건에 맞나요?" 뒤에 붙여 읽혀야 합니다.
- **긍정형**: 제외·불가 문장은 지원할 수 있는 쪽으로 뒤집어 씁니다. "맞아요"가 곧 충족입니다.

| 원문 | 요약 |
| --- | --- |
| "'27년 1학기 휴학예정 학생 제외" | "27년 1학기 휴학 계획 없음" |
| "타 장학금과 중복 수혜 불가" | "이번 학기 다른 장학금 안 받음" |
| "편입학 예정인 학생 지원 불가" | "다른 학교로 편입할 계획 없음" |
| "2026년 상반기 (재)논산시장학회 장학생은 제외" | "26년 상반기 논산시장학회 장학생 아님" |
| "TOEIC 500점 이상" | "TOEIC 500점 이상" |
| "고립·은둔 지원 프로그램을 수료한 자" | "고립·은둔 지원 프로그램 수료" |
| "기부자별 세부 선발기준은 누리집에서 확인" | "누리집의 기부자별 선발기준 충족" |
| "지방 소재(서울·인천·경기도 제외) 대학교 재학생" (`basic`) | "지방 소재 대학 재학생" |
| "학칙에 의한 징계사실이 없는 자" (`basic`) | "징계 받은 적 없음" |

- **섞인 문장**은 학생이 직접 답할 부분만 요약합니다. 필드로 판정한 부분은 넣지 않습니다. 예: "2003년 1월 1일 이후 출생자 중 고등학교 졸업 학력 취득 후 5년이 경과되지 않은 자" → "고교 졸업 후 5년 안 지남"(나이는 `max_age`).
- 원문에 없는 내용(금액, 기간, 대상)을 지어내지 않습니다. 줄일 수 없을 만큼 짧은 원문은 그대로 씁니다.
- 공백을 정리한 뒤 비어 있거나 40자를 넘으면 `null`로 버리고 화면은 원문을 보여 줍니다(`display_name`과 같은 처리).

### 3.2 ✓/✗ 조건 요약 (코드, `requirement`)

`app/matching/describe.py`의 순수 함수 `describe(condition, criteria) -> str | None`입니다. 값이 있는 모든 `ConditionName`에 대해 반드시 문장을 만듭니다. 조건 종류마다 테스트를 둬서, 새 조건이 추가됐는데 요약이 빠지면 테스트가 실패합니다.

| 조건 | 예 |
| --- | --- |
| `target_grades` | `[2, 3]` → "현재 2·3학년" |
| `excludes_extra_semester` | "초과학기 아님" |
| `excludes_new_students` | "신입생 아님" |
| `excludes_transfer_students` | "편입 첫 학기 아님" |
| `min_remaining_semesters` | `1` → "남은 정규학기 1학기 이상" |
| `enrollment_status` | `["재학"]` → "재학 중" |
| `school_excluded` | "충북대학교는 대상 학교 아님" (true일 때만 체크리스트에 나오고 항상 불충족) |
| `min_gpa` + `grade_basis` | `3.5`, `직전학기` → "직전학기 평점 3.5 이상" (기준 없으면 "평점 3.5 이상") |
| `min_score_100` + `grade_basis` | `80`, `전체` → "전체 학기 성적 80점 이상" |
| `min_credits` | `12` → "12학점 이상 이수" |
| `target_nationality` | `domestic` → "대한민국 국적", `foreign` → "외국 국적" |
| `gender` | `여` → "여학생" |
| `max_age` | `26` → "만 26세 이하" |
| `max_income_bracket` | `8` → "소득 8구간 이하", `0` → "기초생활수급자", `0.5` → "차상위 이하" |
| `regions` + `region_basis` | `["충청남도 논산시"]`, `부모` → "부모 주소 충청남도 논산시" |
| `required_special` | `["다자녀"]` → "다자녀" (여러 개면 " 또는 "로 이음) |
| `excludes_full_tuition` | "등록금 전액 감면 안 받음" |
| `target_department` | `소프트웨어학부 포함` → "소프트웨어학부 포함", `소프트웨어학부 불포함` → "소프트웨어학부 외 학과", `불명` → `None`. `제한없음`은 엔진이 비교하지 않아 체크리스트에 나오지 않음 |
| `target_program` | `AIBC 양성인재` → "AI부트캠프사업단 양성인재" |

- 그 필드가 `ambiguous_fields`에 있으면(값을 확정할 수 없음) `None`을 돌려줍니다. 화면은 고정 문구 **"공지 기준이 명확하지 않아요"** 를 보여 줍니다. 코드가 그럴듯한 기준을 지어내지 않습니다.
- `target_department = 불명`도 같은 이유로 `None`입니다.
- 코드가 값으로 만들므로 재추출 전 데이터에도 바로 적용됩니다.

## 4. 데이터·API 변경

### 4.1 추출 스키마 (`app/extraction/schemas.py`, 공용)

```python
class ConditionText(BaseModel):
    text: str        # 공지 원문 그대로 (근거, condition_key의 입력)
    summary: str | None = None  # 3.1 규칙. 비었거나 40자 초과면 None

extra_conditions: list[ConditionText]
basic_conditions: list[ConditionText]
notes: list[str]     # 그대로
```

- `mode="before"` validator가 문자열 항목을 `{text, summary: None}`으로 읽습니다. DB `criteria`(jsonb)에 저장된 v9 이전 결과와 골든셋 정답 JSON이 그대로 읽히므로 Alembic 마이그레이션이 없습니다.
- `condition_key()`는 계속 `text`로 만듭니다. 요약이 바뀌어도 사용자 답은 유지됩니다.
- Gemini에는 `ExtractedCriteria.model_json_schema()`가 그대로 `response_json_schema`로 갑니다(배열 안 객체는 지원됨).

### 4.2 웹 API (`app/schemas/api/scholarships.py`, 공용) — frontend 영향 있음

| 모델 | 변경 |
| --- | --- |
| `ConditionCheck` | `requirement: str \| None` 추가 (3.2) |
| `ExtraCheck` | `summary: str \| None` 추가 |
| `OpenCondition` | `summary: str \| None` 추가 (빠른 확인 카드 질문) |
| `ScholarshipDetail.extra_conditions`, `basic_conditions` | `list[str]` 그대로 (원문) |
| `ScholarshipDetail.basic_items` | 새 필드 `list[ConditionTextOut]`(`text`, `summary`). `basic_conditions`와 같은 순서 |

모든 변경은 **필드 추가**뿐이라 기존 frontend가 그대로 동작합니다. 그래서 T43과 T44의 배포 순서가 자유롭습니다. `basic_conditions`는 T44가 `basic_items`로 옮긴 뒤 다음 정리 때 지웁니다.

- `requirement`는 엔진(`evaluate`)이 `ConditionCheck`를 만들 때 `describe()`로 채웁니다. 엔진은 조건이 `null`·`제한없음`이면 체크리스트에 넣지 않으므로(`rules.py`가 `None` 반환) 그런 조건의 요약은 만들 일이 없습니다.
- frontend는 `npm run gen:api`로 타입을 다시 만들고 화면을 고칩니다(T44). 두 PR을 서로 링크합니다.

## 5. 프롬프트 v10 (`extract_v10.md`)

v9에서 바꾸는 부분만 적습니다.

- 2장 규칙 7: `extra_conditions`·`basic_conditions` 항목을 `{text, summary}`로 쓰고, 3.1 규칙과 표의 예시를 넣습니다. **`text`는 지금처럼 원문 그대로**입니다(규칙 4와 같음).
- 2장 규칙 7 `basic_conditions`: "세부 자격이 같은 공지에 적힌 규정의 출처 문장" 줄을 지우고, 대신 **"어느 목록에도 넣지 않는 문장"** 항목을 새로 둡니다. 세부 자격이 같은 공지에 이어 적힌 규정 출처("1. 기본 자격요건: 「…관리지침」을 따름"), 소제목·번호만 있는 줄이 해당합니다. 외부 기준 참조의 예시 문장도 같은 기준으로 고칩니다.
- `notes`의 "제도·사업 설명" 예시("지방 국립대학교에 진학하는 학생은 …")는 유지합니다.
- `model_version`은 `{GEMINI_MODEL}+extract_v10`입니다.

## 6. 화면 (T44, frontend)

```
✓ 평점  충족
  직전학기 평점 3.5 이상
  ▸ 근거 보기                ← <details>: 원문 근거 + 출처

? 소득분위  모름
  공지 기준이 명확하지 않아요
  ▸ 근거 보기

? 다른 장학금 중복  눌러서 답하기     ← 직접 답하는 조건
  이번 학기 다른 장학금 안 받음
  "타 장학금과 중복 수혜 불가"        ← 원문 2줄까지, 넘으면 "더 보기"
```

- **내 정보로 판정한 조건**: 조건 이름 + 판정 + `requirement` 한 줄. `requirement`가 없으면 "공지 기준이 명확하지 않아요". 원문 근거와 출처는 `<details>`("근거 보기")로 접습니다.
- **직접 답하는 조건**: 굵은 줄에 `summary`를 씁니다(없으면 지금처럼 `conditionLabel(text)`). 그 아래 원문을 회색 글씨로 2줄까지 보여 주고, 넘으면 "더 보기"로 펼칩니다.
- **빠른 확인 카드**: "이 조건에 맞나요?" 아래 질문을 `summary`로 쓰고(없으면 원문), 원문을 작은 글씨로 함께 보여 줍니다.
- **지원 전 확인**(`basic_items`): 목록 항목을 `summary`로 쓰고(없으면 원문), 원문은 접습니다. **참고 안내**(`notes`)는 그대로입니다.
- 개인정보처리방침의 "해당돼요 / 아니에요"를 화면과 같은 "충족 / 불충족"으로 고칩니다.

## 7. 검증

| 무엇 | 어떻게 |
| --- | --- |
| 스키마 호환 | 문자열 목록(v9 이전)·객체 목록(v10)이 모두 읽히는지, `summary` 40자 초과·빈 값이 `None`이 되는지 테스트 |
| 답 보존 | 같은 `text`에 `summary`만 다른 두 결과에서 `condition_key`가 같은지 테스트 |
| 코드 요약 | `describe()`가 `ConditionName` 전부에 대해 값이 있으면 문장, 모호하면 `None`인지 테스트(조건마다 1개 이상) |
| API | 상세·목록 응답에 `requirement`·`summary`가 실리는지, 예전 데이터는 `summary = null`인지 테스트 |
| 추출 정확도 | 실제 Gemini로 `uv run python -m eval.run`을 실행해 v9와 필드 정답률·needs_check를 비교. 떨어지면 원인을 보고 |
| 요약 극성 | eval 결과 JSON에 `condition_summaries`(공지·장학금·목록·`text`·`summary`)를 넣고, 머지 전에 사람이 전부 읽어 극성과 지어낸 내용이 없는지 확인 |
| 출처 문장 제거 | eval 결과에서 sw_dept_1154016의 "관리지침을 따름"이 세 목록 어디에도 없는지 확인 |

## 8. 배포 뒤 (사람이 할 일)

1. T43 배포 뒤 관리자 화면에서 모집 중·상시 공지를 재추출합니다. 수집 1회에 20건씩 처리되므로 공지 수에 따라 여러 번 걸립니다.
2. 아래 쿼리로 남은 공지가 없는지 확인합니다.

```sql
select n.model_version, count(*)
from scholarships s join notices n on n.id = s.notice_id
where s.status in ('OPEN', 'ALWAYS')
group by 1;
```

3. T44를 배포합니다. API 변경이 필드 추가뿐이라 T43 배포 전후 어느 때든 기존 화면이 깨지지 않습니다. 다만 T44는 새 필드를 쓰므로 T43이 먼저 배포돼야 요약이 보입니다. `summary`·`requirement`가 `null`이면 원문을 보여 줍니다.
